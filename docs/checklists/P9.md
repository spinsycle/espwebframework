## Part A: 24 hour soak (NodeMCU, p8b firmware)

Started 2026-11-17 about 22:15 with `tools/soak.py` writing `soak.csv` in the repo. Setup on the board: `soak_pwm`, `soak_in`, repeating sequence `soak_q` (PWM 50 % / 0 every 20 s), repeating timer `soak_t` (60 s) with rule `soak_r`, all failsafe 0. No browser tab left open and hidden.

| #   | Check                                                                                                                                | NodeMCU | ESP32 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | ------- | ----- |
| A1  | The logger ran the full 24 h and printed `soak done` (no early exit, PC did not sleep)                                                |         |       |
| A2  | Restarts 0 (uptime in `soak.csv` never goes down), reset reason never watchdog or exception, `wd` and `fault` columns all 0            |         |       |
| A3  | Heap low-water (`heap_min_free`) does not trend down over the day (it started at 9216) and stays above 3 KB                            |         |       |
| A4  | Errors column: 1 at t=774 s (a missed poll while the PC was busy); any others are explained or the run is repeated                     |         |       |
| A5  | After the run, the Automation tab still shows the sequence running and the timer finishing, and the dashboard still switches a device |         |       |

**Result of the first soak (ended 2026-11-18): FAILED, rows A1-A5 stay unticked.** 13,276 passes, 666 failed polls, 3 restarts, lowest heap low-water 3,224 bytes.
- Restarts at t=1,257 s, 56,330 s and 71,030 s, all reset reason `External System` (the reset pin, not the watchdog and not an exception; `wd` and `fault` stayed 0). Something outside the firmware toggled reset (a serial port opened on COM4 does this); not yet explained.
- Heap: stable at about 14.9 KB free for the first 10 hours, then from hour 10 on it dipped (free down to 7.7 KB, largest block down to 2.2 KB, low-water 3.2 KB at t=55,969 s) while `ws_clients` was 0, so the dips came from HTTP requests, not browser tabs. It recovered each time.
- Errors: nearly none in hours 0-9, then clusters of up to 76 polls in a row from hour 10, and from about t=79,441 s the board stopped answering altogether (ping 100% loss on 192.168.4.23 at the end; no serial output). Cause unknown.
- The logger itself is a suspect: it opens three short connections every 5 s, and the ESP8266 is known to refuse new connections for minutes after a burst. Next run should poll less often (one request, every 15-30 s) and log what the PC sees (ping) beside it.

**Second soak (2026-11-18 22:28 to 2026-11-19 22:28, one request every 20 s plus a ping): memory passes, the strict criteria still fail.** 3,965 passes, 204 failed polls, 3 restarts, lowest heap low-water 6,440 bytes.
- Heap: flat. Average free 14.8-15.0 KB in every 4-hour block, largest block never below 6.9 KB, no downward trend and no 2-3 KB dips (those were the first logger's three connections per poll). `wd` and `fault` 0 all day, loop gap never above 885 ms (the boot value). No leak and no firmware-caused restart. This is the evidence for tracker item 44.
- Restarts: Thu 14:19, 14:21 and 15:11, all `External System` again, and clustered in the afternoon like the first run's (about 13:50, 17:55). With the power-cycle after the first run reporting the same reason, this reads as the board losing power or being reset from outside (USB port, cable, PC activity during the day), not the firmware. Not proven: next run on a wall adapter instead of the PC's USB port.
- Failed polls: 113 had HTTP fail with ping ok (board on the network but not answering new connections, typically for 2-30 minutes in clusters, worst Thu 17:14-17:48), 57 had ping fail with HTTP ok (a lossy Wi-Fi link), 91 had both. The board recovered by itself every time except through the three restarts. So the ESP8266 does stop accepting new connections for a while, even at one request per 20 s; this belongs in `docs/SAFETY.md` as a known limit.
